# Approach and limitations

## Approach

1. **Read the test.** `testscribe run` accepts a starting URL and a plain-English test case, or `--case-file` with `url`, `test`, and optional `vars_file`. The CLI resolves the selected provider preset (BharatCode, Gemini, or Groq), optional connection overrides, variable values, and report directory. Variable names starting with `_` mark values to substitute locally and redact before model requests and report writes. The VS Code extension and MCP server invoke this same CLI.
2. **Check and plan.** Before opening a browser, the runner checks that the starting URL responds. It asks the model for an ordered list of action intents and explicit checks, including when each check should run. It rejects plans without usable checks and limits a run to 12 actions and 20 model calls.
3. **Open the page.** Playwright starts Chromium in a fresh browser context and visits the starting URL.
4. **Observe each step.** Before every planned action, the runner takes a new accessibility snapshot of the current page. For large pages, it keeps navigation controls and relevant named sections to reduce the observation sent to the model.
5. **Choose and execute the action.** An unambiguous observed click can be selected directly; otherwise the model chooses an action using a role and accessible name. Python requires exactly one live target, then clicks, fills, selects a native dropdown, or presses a supported key. If a target is ambiguous, it inspects live matching controls and their surrounding context before asking the model again. A repeated click without new input or navigation is blocked when it makes no progress. Direct navigation is allowed only to a URL written in the test case and checked with cURL; other navigation uses page controls.
6. **Verify at the requested point.** Python checks each requested condition after its assigned number of actions. This lets it verify that a Save button is enabled before clicking it, then verify a saved state afterward. It waits briefly for dynamic content. The model's claim of success is never used as the verdict.
7. **Write the result.** The command returns `PASS` when every check matches, `FAIL` when an assertion is unmet, and `BLOCKED` when setup, planning, browser actions, or the model provider prevent a reliable run. `failure_stage` distinguishes where a nonpassing run stopped; an unmet assertion alone does not prove an application bug. `report.json` records the plan, attempted steps, checks, final URL, timing, and model usage. With `--json`, the CLI also prints a compact, versioned result for agents and VS Code. The MCP server returns a run ID immediately, then lets an agent poll for this same result. Passing runs save a final-page screenshot by default; `--no-pass-screenshot` skips it. Nonpassing runs save a screenshot and Playwright trace when a page is available. Marked sensitive variables suppress all these artifacts unless explicitly allowed.

The same runner has passed four-action cases on PHPTRAVELS, Selenium's web form, and The Internet using both BharatCode Qwen and the optional Gemini configuration. These are individual demonstrations, not a reliability benchmark.

## Limitations

- The model can misunderstand a case, omit an explicit step, or plan a check weaker than the intended outcome. The runner does not mechanically prove that every requested action appears in the plan. Review the plan and executed steps in the report for important flows. For example, seeing “Stripe” after selecting a Payments filter does not prove the filter worked if Stripe was already visible beforehand.
- The runner relies on accessible controls and a unique role/name match. Ambiguous or missing targets block the run. Visual-only controls, iframes, downloads, CAPTCHA, complex widgets, and automatic dismissal of unexpected popups are outside this version's tested scope.
- Live sites can change, load slowly, or reject automation. Model APIs can be slow or temporarily unavailable. The Qwen and Gemini runs above were single trials, so their pass rates and speed should not be treated as a provider comparison.
- Exact-match redaction covers marked values and their URL-encoded forms, including values embedded in other text. It cannot promise secrecy if a site transforms a value into an unrecognized form. Unmarked variables can be shown to the model. The target site receives every filled value.
- Reports, screenshots, traces, and videos are local artifacts. Sensitive runs omit image/trace/video evidence by default; `--allow-sensitive-artifacts` opts back in. Artifacts can contain typed values, so keep them out of Git.
- The VS Code extension requires a separate Python/Chromium installation. The MCP server requires Python 3.11+ and an agent configured to start its local stdio process; installing the portable skill alone does not add MCP tools.
